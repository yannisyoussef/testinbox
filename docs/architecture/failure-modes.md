# Failure-Mode Analysis

| Failure | Handling |
|---|---|
| Same provider delivery event reprocessed (e.g., SES/SNS redelivery) | Deduplicated per recipient via unique constraint on `(provider, providerMessageId, envelope recipient)` — a no-op (ADR-019 as amended by ADR-026). |
| One provider event carrying several envelope recipients | One `Message` row per recipient, all inserted and notified in a single transaction; the composite delivery key stops the first recipient from suppressing the rest (ADR-026). |
| Persistence fails partway through a multi-recipient delivery | The whole transaction rolls back and the adapter returns SMTP `451`; the sender retries the transaction as a unit, so no recipient can receive an infrastructure-induced duplicate. Blobs written before the failure stay charged to their reservations until cleanup proves and deletes them (ADR-035); the orphan sweep is the backstop. |
| Sender MTA retries after gateway crash between persist and `250 OK` | Surfaced as a second `Message` row annotated `possibleDuplicateOfMessageId` — never silently suppressed, because a byte-identical retry is indistinguishable from a genuine duplicate send by the SUT, which TestInbox must expose (ADR-019). |
| SUT genuinely sends the same email twice (byte-identical) | Two `Message` rows, faithfully observable — content-based dedup is explicitly forbidden (ADR-019). |
| Malformed/unparseable MIME | Raw MIME already persisted before parsing is attempted; message stored as `ParseFailed`, retrievable via `/raw`, does not satisfy field matchers. |
| MIME/zip/archive bomb | Size and decompression-ratio limits enforced during parsing in the isolated `ingestion-gateway` process; parsing aborted and message marked `ParseFailed` with a reason code rather than exhausting memory/CPU. |
| Two concurrent `createInbox()` calls collide on the same generated token | Prevented by DB unique constraint on the address column; a collision triggers a regenerate-and-retry inside the same request, invisible to the caller. |
| Requested address collides with an existing reservation | `GENERATED` mode: alias is a prefix hint plus random token, regenerate-and-retry on the negligible token collision. `EXACT` mode: the Postgres unique constraint picks one winner; the loser receives `409 Conflict` (ADR-021). |
| Email arrives for an unknown/expired inbox | Accepted at SMTP level, content discarded immediately and never stored (metadata-only logging) — not attributed to any inbox (ADR-025, `inbound-mail-flow.md`). |
| Email arrives microseconds before inbox creation completes | Cannot occur: the address does not exist as a routable token until the creation transaction commits, so no SMTP session can resolve it earlier. |
| Email arrives during inbox expiry window | Honored if the inbox was still `Active` at the moment of persistence; see the `Expiring` grace period in `message-lifecycle.md`. |
| Wait subscriber's connection drops mid-wait | Server tears down the subscription on disconnect; no resource leak, no side effect. |
| API node's `LISTEN` connection drops while a message commits | Notification is lost (Postgres notifications are ephemeral), but on re-`LISTEN` every parked waiter re-runs its query once, finding any message committed during the gap; prolonged disconnection degrades to bounded-interval re-query (ADR-020). A waiter can never sleep past a persisted match. |
| Gateway crash between object-storage write and DB commit | Orphaned blob (never a DB row pointing at missing data — write order per ADR-005); reclaimed by a periodic orphan sweep deleting objects older than a threshold with no referencing row. |
| Postgres unavailable | API and ingestion both fail closed (503 on writes/reads); no in-memory fallback that could silently lose messages. Ingestion-side SMTP `4xx` (soft failure) is returned to the sending MTA so it retries later rather than the message being lost or bounced permanently. |
| Storage accounting ledger drifts from the rows (ADR-035) | Cannot happen through the normal paths: the triggers write rows and deltas in one transaction, and compaction moves bytes atomically. If a defect or manual SQL causes drift, the 6-hourly reconciliation finds it from one snapshot, repairs `base := derived − Σdelta`, and meters it (`storage_accounting_drift_total`). A failed compaction pass rolls back with its deltas intact and retries on the next tick. The TI-STORAGE-002 admission core would read the ledger, but no ingress path calls it yet, so drift cannot yet affect mail. |
| Object storage unavailable | ADR-035 guarded path (TI-STORAGE-003). An upload that cannot connect is definitive: the event's reservations are released at once. One that times out, resets or gets a `5xx` is ambiguous: the reservation stays charged, the ambiguity is persisted, and the key keeps its write slot. Either way the node's breaker opens, the whole `DATA` gets `451`, and nothing becomes visible. While the breaker is open, later events get `451` before any slot or reservation, and before any recipient resolves, so an unknown recipient gets the same `451` as a known one. The breaker remembers every kind it opened on. After a backoff (15 s doubling to 2 min), a zero-byte probe closes it (and a fresh in-bound measurement, if a clock offset opened it). For a quota `400`, the trial is a real event instead. |
| An upload's response is lost after its full body (probe E5) | Ambiguous, never "absent": the object may exist. The reservation stays `RESERVED` and charged. At the deadline, cleanup moves it to `RELEASING` (`release_not_before = deadline + S`), then releases it only after a storage witness plus `C_drain` and a per-exact-key proof that the object and any multipart upload are absent. The ambiguity row keeps its write slot until verification at `T_verify` (60 min). |
| A late object (a commit that lands after cleanup deleted the key) | The **admission latch** is set and committed first, then the object is deleted, metered as `late_object`, and the reservation stays charged `S` longer. Every ingestion node answers `451` before T1 until an operator investigates and clears it by hand (no endpoint clears it). Each cleanup row is its own transaction, so a storage error on another row cannot undo the latch. The same holds at ambiguity verification, and for an orphan the sweep deletes whose key was ambiguous within 24 h. |
| The ingestion process dies mid-event | Nothing it wrote is visible: T2 never ran. Its reservations stay charged until cleanup proves their keys absent. At the next start, its unclean generation is turned into keyless ambiguity for the uploads it had started (`first_upload_at`), capped at the node's 16 slots. A restart therefore cannot start more ambiguous uploads than the finalize budget H covers. Every key it had started also gets a coverage row, proved present or absent at `verify_at` like any ambiguous key, so a frozen writer's late commit latches instead of vanishing into the orphan sweep. Cleanup does the same for a node whose heartbeat went stale; if that node was in fact alive, its next heartbeat re-registers it. A node that could not persist an ambiguity never marks itself clean at shutdown. Any throwable after an upload began, an `Error` included, is treated the same way: the ambiguity is persisted, or the slot is poisoned, before the slot could be reused; an `Error` then still propagates. |
| No write slot free within `W_slot` (10 s), or the T1 admission lock not granted within 5 s | `451` for the whole `DATA`, with no reservation made. It is infrastructure, never `SERVICE_CAPACITY`. |
| DB↔storage clock offset above `ε_max` (30 s) | The ingestion node's breaker opens (`451`), and cleanup suspends every release. Whichever of them observes the offset first holds every reservation, `RESERVED` or `RELEASING`, in the database until at least `write_deadline_at + S + offset` (`greatest()`, so repeated observations never compound and nothing moves earlier). The hold lives in the rows, not in memory: a restart after the clocks recover cannot release early. |
| Cleanup and T2 race for one reservation | They serialize on the row. T2 holds it `FOR UPDATE`, and cleanup's claim `SKIP LOCKED`s past it. If cleanup claimed it first, T2 finds it `RELEASING`, answers `451` (fenced), and commits nothing. Committed content is never deleted: cleanup deletes only its own reservation's exact keys, and only when no message row has that id. |
| Redis unavailable (once introduced) | Wait fan-out and rate limiting degrade gracefully (short-interval fallback polling / fail-open or fail-closed per rate-limit policy — a decision left to the relevant ADR when Redis is actually introduced), never a hard outage of core ingestion. |
| Ingestion-gateway node crash mid-parse | Raw MIME already durably stored; on restart (or another node), no work is lost beyond re-attempting parse for messages left in a transient state, driven by a bounded retry/reaper. |
| Malicious/hostile attachment (filename attack, path traversal in filename, disguised executable) | Filenames are never used as storage paths (object storage keys are attachment IDs, not filenames); original filename is stored only as metadata and re-escaped on any UI/API rendering. |
| SSRF via message content (remote images, tracking pixels, hostile links) | TestInbox never auto-fetches remote URLs found in message content; extracted links are surfaced as data only (ADR-011, `docs/security/threat-model.md`). |
