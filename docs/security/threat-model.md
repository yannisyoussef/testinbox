# Threat Model

Received email content is untrusted input from arbitrary third parties (the
message sender is not necessarily the TestInbox account holder — anyone who
learns or guesses/enumerates an address can send to it).

> **Correction, 2026-11-06: the inbound edge is internet-facing.** Since the
> owner-only beta launch of 2026-10-28 the production Postfix edge listens on
> public tcp/25 and `inbox.testinbox.email MX 10 mx1.testinbox.email` is
> published, so **any Internet host can open an SMTP session to the edge and
> send mail addressed to the tenant domain**, with no account. Earlier
> project text described the edge as "dormant" with "no public MX"; that was
> superseded on 2026-10-28 and is corrected on the owner's statement (#124,
> comment 6686330363). Dates and Ops' launch and acceptance records:
> [`mail-edge-contract.md` § Correction](../architecture/mail-edge-contract.md#correction-2026-11-06-the-edge-is-internet-facing).
> Inbox creation and message access stay authenticated; self-service sign-in,
> participant admission and storage enforcement stay closed under their own
> authorizations. Every row below, and every future analysis, treats the edge
> as internet-facing. The inbound-SMTP rows at the end of the table were added
> by this correction.

| Threat | Mitigation |
|---|---|
| Stored XSS via HTML email body | HTML is never rendered at the primary `testinbox.email`/`api.testinbox.email` origin. Rendered only in a sandboxed iframe on an isolated origin (e.g., `usercontent.testinbox.email`) with a strict CSP (`script-src 'none'`), `sandbox` attribute without `allow-same-origin`+`allow-scripts` together, and no cookies set on that origin. See [ADR-011](../adr/0011-html-rendering-security.md). |
| Malicious/hostile HTML (obfuscation, CSS exfiltration tricks) | Sanitization pass strips/neutralizes `<script>`, event handlers, `javascript:`/`data:` URLs in dangerous contexts, and CSS-based exfiltration vectors before any rendering; raw HTML remains available via `/raw` for cases where a test intentionally asserts on the unsanitized source. |
| Tracking pixels / remote resource loading | Remote image/resource loading is not automatically performed by TestInbox's own systems; if the sandboxed viewer loads remote resources at all, it goes through a proxy that strips tracking query params and never forwards the recipient's real IP/identity — proxying vs. blocking entirely is a decision for the security-focused ADR pass at implementation time, but auto-fetch-with-no-mediation is rejected outright. |
| Malicious SVG (embedded `<script>`/`<foreignObject>`) | SVG treated as an attachment/asset like any other hostile HTML surface: never inlined into the primary origin's DOM; served with `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff` when downloaded directly. |
| MIME bombs / decompression bombs | Size and nesting-depth limits enforced during parsing in the isolated `ingestion-gateway`; exceeding limits aborts parsing (message becomes `ParseFailed`) rather than exhausting memory/CPU. |
| Malformed MIME (parser exploitation attempts) | Parsing runs in a process/module boundary isolated from the API (`ingestion-gateway`), limiting blast radius; parser fed a corpus of adversarial MIME in tests (`docs/quality/strategy.md`). |
| Malicious attachments (executables, disguised types) | Not executed or previewed inline; served only as opaque downloads with sanitized `Content-Disposition` filenames; content-type sniffing disabled (`nosniff`) so a browser won't reinterpret a malicious file as HTML/script. |
| Archive bombs within attachments | Attachments are stored and served as opaque bytes; TestInbox does not automatically decompress/expand archive attachments server-side in MVP, avoiding the bomb-expansion attack surface entirely. |
| Filename attacks (path traversal, homoglyphs, overlong names) | Object storage keys are always generated attachment IDs, never derived from the sender-supplied filename; the original filename is stored as metadata only and re-escaped wherever displayed. |
| SSRF via extracted URLs | TestInbox never auto-fetches URLs found in message content; link extraction is data-only. Any future "preview a link" feature would require its own SSRF-hardened fetch path (deny-list of internal IP ranges, no redirects to internal networks) — not built in MVP. |
| Authorization bypass / cross-project resource access | Every resource fetch is authorized against the caller's workspace/project derived from their API key, never from a trusted path parameter alone; cross-tenant access is treated as a security bug (see [`docs/api/principles.md`](../api/principles.md)). |
| API key leakage | Keys are opaque, verifier-only at rest (the plaintext is never stored, so it cannot be shown again or recovered — [ADR-032](../adr/0032-api-key-credential-lifecycle.md) §4), scoped (least privilege), individually revocable, and identified by a non-secret public handle so an operator can name one without quoting it. A workspace holds many keys, so a leaked CI credential is revoked alone rather than by rotating a shared secret. Revocation is effective on the next request on every node — no authorization state is cached. SDKs model the secret on a type distinct from metadata and keep it out of `toString`; the credential never reaches a log, a metric label, an error body or an audit event, and `ApiKeySecretLeakTest` proves it by searching captured debug-level logs and every other representation. |
| Stolen credential replayed after revocation | Every request resolves the credential from the database; there is no cache, and therefore no staleness window. The bound is zero requests and zero seconds, asserted end-to-end (`ApiKeyAcceptanceTest`) and against a deployed environment (`deploy/synthetic/product/`). |
| Brute-force guessing of a credential | The secret carries 260 bits of CSPRNG entropy and the format enforces its length on the way in and out, so guessing is infeasible by construction rather than by rate limiting. This is also why the verifier is SHA-256 rather than a password KDF: there is no dictionary to slow down, and a deliberately slow hash on the authentication path would convert cheap unauthenticated requests into expensive server CPU (ADR-032 §2). |
| Privilege escalation through key minting | A key can never grant a scope its creator does not itself hold, so `api-keys:manage` is not a superuser scope by accident. Workspace and project always come from the authenticated credential; no request field selects them. |
| Bootstrap credential becoming the permanent model | Two conditions, both required. It authenticates only while its workspace holds no usable managed administrator — evaluated per request, so it closes its own window with no restart and no operator action and therefore cannot be forgotten — **and** only while the presented token matches the value the process is currently configured with, so rotating or unsetting the setting genuinely retires it (ADR-032 §8). A deployed node also refuses to start unless the configured value is long, high-entropy and not a known fixture. |
| Idempotency-key squatting or table exhaustion | Records are created only by committed successful mutations, so growth is bounded by the rate and quota budgets that already bound resource creation ([ADR-033](../adr/0033-idempotent-mutations.md) §4), and expire after a configurable retention (six hours by default). Binding a key requires a credential inside the workspace — already inside the tenancy boundary — so the residual risk is intra-workspace. That risk is not only accidental collision between two CI systems sharing a key scheme: a credential holding just `inboxes:write` can deliberately pre-bind a predictable key such as `build-1234` with a different fingerprint, at the cost of one inbox creation, and the victim job then gets `409 idempotency-key-reused` for the whole retention window with no endpoint to clear it. Workspace scoping is still the right boundary — narrowing it to the credential would defeat the rotation guarantee it exists for — but note that ADR-032 makes credentials individually scoped precisely so one CI credential cannot interfere with another's work, and this is a gap in that. Mitigated by unguessable key prefixes rather than by the platform. |
| Cross-tenant replay via a guessed idempotency key | Records are scoped to the workspace, and the stored key is `SHA-256(workspace ‖ operation ‖ key)`. The same key value in two workspaces is neither a collision nor detectable as a match. The scope is derived from the authenticated credential and never from a request field. |
| Global-capacity inference via authenticated storage visibility or the wait `409` | A tenant learns one bit (`SERVICE_CAPACITY`) and only about its own copies; no response carries a global limit, global stored/reserved/available bytes, a node or reservation figure, or another workspace's state, and the `409` for `SERVICE_CAPACITY` omits `quota`/`limit`/`current` entirely. Every visibility query is workspace-scoped in the SQL and selects no unscoped sum; cross-tenant inbox ids are `404`. Proven structurally by `StorageDisclosureTest` and `StorageVisibilityTest`; the accepted residual (admitted-prefix probing) is recorded in [`abuse-model.md`](abuse-model.md) and [ADR-035](../adr/0035-physical-storage-bound-at-ingest.md) §13d. |
| Denial of service (volumetric or resource-exhaustion) | Rate limiting per API key/workspace (`docs/security/abuse-model.md`), size/nesting limits on MIME parsing, capped wait-request duration and count of concurrent waits per inbox/workspace. |
| *Inbound SMTP rows added 2026-11-06 for the internet-facing edge.* | |
| Recipient enumeration over SMTP (attacker: any Internet host) | Unchanged and still required: [ADR-025](../adr/0025-unknown-recipient-handling.md)'s uniform `250` after `DATA`. The edge validates no recipient (`relay_recipient_maps` empty), relays every tenant-domain recipient, and ingestion discards unknown ones in-process with nothing persisted. `postmaster@` answers like any other recipient. Proven in the rehearsal through real Postfix (`deploy/synthetic/edge/contract.test.mjs`, `scripts/mail-edge-storage-proof.sh`). The edge stores and forwards, so an Internet sender sees the **edge's** replies, never ingestion's: an ingestion `451` becomes a deferral in the edge queue, not a reply, provided the edge emits no DSN (see the DSN row). Gaps recorded in [`mail-edge-contract.md` § Known gaps](../architecture/mail-edge-contract.md#known-gaps) (no VRFY/EXPN behavioural probe; `smtpd_recipient_restrictions` unpinned) are open. |
| Limit, quota, capacity or timing disclosure over SMTP | Unchanged: [ADR-035](../adr/0035-physical-storage-bound-at-ingest.md) I9 gives every syntactically valid recipient the uniform `250`, including a reached inbox, workspace or service ceiling. Every accepted residual in this area has an **authenticated** observer, not an anonymous sender: the capacity residuals (ADR-035 §13d, [ADR-037](../adr/0037-bounded-cohort-storage-and-disclosure.md) §6; [`abuse-model.md`](abuse-model.md)) are read from a workspace's own refusal records and `SERVICE_CAPACITY` diagnostic, and the owner's bounded timing-disclosure exception to I9 for the initial beta (2026-11-06, #124 comment 6675385078; recorded on #136, not yet on `develop`) is observed by an authenticated participant timing its own co-addressed copy. A public edge lets an anonymous sender put mail into the system but not read those signals, because the edge stores and forwards: an ingestion `451` becomes edge-queue delay, not a reply. That argument holds only while the edge emits no DSN and no client can reorder retries, so it depends on the ETRN and DSN rows below. Participant admission is closed, so today the authenticated observers are operator-provisioned workspaces only. |
| Open relay (attacker: any Internet host relaying through the edge) | `smtpd_relay_restrictions = permit_mynetworks, reject_unauth_destination` with `mynetworks` pinned to loopback; outbound tcp/25 blocked at the host (Ops). The rehearsal refuses a foreign domain from a client outside `mynetworks` with `554`. **Tracked, not closed:** relay-bypass address shapes (percent-hack, source route, bang path) are not probed and `allow_percent_hack`/`swap_bangpath` are unpinned ([known gaps](../architecture/mail-edge-contract.md#known-gaps)). |
| Client-triggered queue flush (ETRN) | **Open; fix proposed in draft [#147](https://github.com/yannisyoussef/testinbox/pull/147)** with Ops' lockstep host change. The contract sets neither ETRN key, and Ops confirmed the live edge advertises ETRN for the tenant domain, so any Internet client can force an immediate retry of every deferred message: a retry storm against ingestion that overrides the retry schedule. Fix: `smtpd_etrn_restrictions = reject` and an empty `fast_flush_domains`, in `infinity-core` and in the contract here. Not closed until both land and Ops verifies a `5xx` for `ETRN` on the live edge. |
| Delivery status notifications (DSN) | **Open; fix proposed in draft [#147](https://github.com/yannisyoussef/testinbox/pull/147)** with Ops' lockstep host change. The contract forbids DSNs structurally (`default_transport = discard`, `notify_classes` empty, `bounce_queue_lifetime = 0`), but EHLO advertises the DSN extension, and #147 reports that on the rehearsal image the edge generated notices on a client's request (`NOTIFY=SUCCESS`), some relayed into ingestion: a delivery signal and a backscatter vector. Not closed until the fix lands and the live edge is verified. |
| SMTP flood / edge resource exhaustion | Per-client anvil ceilings (connection count, connection rate, message rate) and the 15 MiB size ceiling on the edge, then ADR-027 ingestion rate limits per workspace. Connection-count and connection-rate refusals are driven to refusal at production values; the message-rate ceiling is asserted statically only. **Tracked, not closed:** `postmaster@`'s Maildir on the edge is unbounded ([known gaps](../architecture/mail-edge-contract.md#known-gaps)). |
