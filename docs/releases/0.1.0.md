# TestInbox 0.1.0 — first release (candidate)

**Status:** release candidate prepared from `develop`; not deployed to
production, not published. The owner decides the merge to `master` and the
production handoff (`docs/dev/release-process.md`).

## What it does

TestInbox gives automated tests a deterministic way to receive email: create
a disposable inbox, point the system under test at its address, and wait —
bounded, race-free, without polling — for the matching message.

Supported in this release, and proven by the test suites and the staging
synthetic gate:

- **Authentication** with workspace-scoped API keys: a bootstrap key per
  deployment, managed keys created, listed and revoked through the API, only
  SHA-256 verifiers stored (ADR-032).
- **Inboxes** with a TTL, in `GENERATED` or `EXACT` address mode; `EXACT`
  local-parts are reserved exactly once with a cooldown after release
  (ADR-021); creates are idempotent (ADR-033).
- **Inbound SMTP** over the environment's private path (the dedicated mail
  edge stays dormant in this release): real MIME parsing (text,
  HTML, links, attachments; `message/rfc822` kept whole), raw MIME stored
  first in object storage and retrievable byte for byte, parse failures kept
  as `parseStatus=FAILED` with the raw message still readable (ADR-005),
  recipient-scoped delivery identity and no content-based de-duplication
  (ADR-019, ADR-026), uniform SMTP replies that reveal nothing about which
  addresses exist (ADR-025).
- **Deterministic waits** (`POST /v1/inboxes/{id}/messages/wait`): check,
  subscribe, re-check, park; woken by PostgreSQL LISTEN/NOTIFY with a bounded
  degraded re-query if the listener drops; window expiry is a `200 TIMEOUT`
  with diagnostics, never an error (ADR-012, ADR-020). An inbox that expires
  or is deleted while a wait is parked ends that wait with `410` promptly and
  never hands it a message afterwards (issue #87).
- **Lifecycle**: `ACTIVE → EXPIRING → EXPIRED` on the TTL with a grace
  period, explicit delete, hard deletion of rows and objects by the sweep.
- **Limits**: per-workspace rate limits and inbox quotas keyed on the
  workspace (ADR-027); storage usage figures for the workspace and each inbox
  (ADR-035 §13), observational in this release.
- **Errors** as RFC 7807 problem documents under
  `https://testinbox.email/problems/...`.
- **SDKs**: `email.testinbox:testinbox-client` (JVM, Java 17 bytecode,
  tested on 17/21/25) and `@testinbox/client` (npm, Node ≥ 22, tested on
  22/24/26), each hand-designed over the same REST contract (ADR-014,
  ADR-023), with typed errors for timeouts, gone inboxes, rate limits,
  quotas and storage refusals. Attachment metadata is exposed; attachment
  bytes are retrieved over REST only in this release.
- **Web inspector** (Next.js): browse an inbox and inspect a message, with the
  untrusted HTML rendered only in a sandboxed iframe under a
  `default-src 'none'` policy and links shown as text (ADR-011).

## Access and installation

- **Service**: not public. Staging is dark (no MX record); the first
  production deployment is dark too (`docs/dev/production.md`,
  `docs/dev/production-smoke-test.md`).
- **SDKs**: built from source until publishing is decided:
  `sdk/kotlin` (`./gradlew build`, Java 17 baseline) and `sdk/typescript`
  (`npm ci && npm run build`, Node ≥ 22). Neither is on Maven Central or
  npm yet (`docs/sdk/distribution.md`).
- **Local development**: `docs/dev/local-setup.md` (JDK 25, Docker, a GHCR
  login for the mirrored MinIO image).

## Compatibility

- REST v1 is contract-first and backward-compatibility-gated in CI
  (ADR-022); additive changes only.
- Backend runtime: Java 25, PostgreSQL 16, an S3-compatible object store
  (the pinned MinIO mirror, ADR-035 §9a). Deployed processes refuse readiness
  until the schema matches the migrations they bundle (ADR-029).
- SDK baselines: JVM 17+, Node 22+ (ADR-023).
- Dependencies: Jackson 3.1.7 / 2.21.7 (ahead of the Spring Boot 4.1.1
  BOM, which manages versions with fixable HIGH findings), Tomcat 11.0.25,
  and the runtime image takes Alpine's security updates at build time.
  Images are scanned under the promotion policy (`scripts/scan-images.sh`)
  before a candidate can be merged to `master`.

## Known limitations and operational constraints

- **Storage enforcement is `OFF`** (`TESTINBOX_STORAGE_ENFORCEMENT=OFF`) on
  every environment by owner decision. The full ADR-035 protocol runs
  (reservations, the fenced write path, accounting, cleanup, the breaker and
  the admission latch), but no inbox, workspace or global storage ceiling
  refuses mail, and the physical containment of ADR-035 Amendment 2 is
  **not** in force. Enabling `TENANT_LIMITS` or `ALL` is an Ops action gated
  by the activation barrier and the filesystem qualification
  (`docs/architecture/storage-activation.md`); production refuses both modes
  outright until the public-boundary work (issues #88–#93) is done.
- **No public SMTP**: no MX record and no public TCP/25. Mail reaches the
  service only through the private edge the environment owns.
- **The physical storage bound is not enforced**, so disk exhaustion of the
  object store is prevented by Ops capacity and monitoring, not by
  admission; a full store answers `451` (the `STORAGE_FULL` breaker) and,
  without the Ops observation monitor, needs an operator restart to recover.
- **One workspace per API-key lineage**; no multi-workspace RBAC, no
  tenant-facing workspace provisioning (issue #80 covers an operator path).
- **Attachments** are stored and served as received: no malware or
  archive-bomb scanning.
- **The web app** manages no credentials and is a debugging tool.
- **Public SMTP activation** (ADR-025 / Amendment 2 §A2.7) and storage
  enforcement activation are separate later milestones with their own gates.

## Deferred to later releases

Custom and customer domains, webhooks, the AWS SES adapter, `TestRun` as a
tracked entity, attachment scanning, framework integrations (Playwright,
Cypress, JUnit/TestNG extensions), a CLI, Python/.NET SDKs, and per-workspace
footprint fairness (issues #90–#92).

## Security-relevant operational constraints

- API keys are stored only as SHA-256 verifiers and never logged; the
  bootstrap key must be long and high-entropy and is break-glass only.
- Every query is workspace-scoped; cross-tenant lookups answer `404`.
- Untrusted HTML is never rendered on the primary origin; links are never
  fetched by the service.
- Management endpoints live on a private port and are not routed by the edge.
- Backups never contain tenant content (`deploy/backup/scope.txt`).
- The production process refuses to start unless the ADR-034 identity,
  domain, HTTPS, database, bucket and timeout invariants hold.
